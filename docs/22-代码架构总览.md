# 代码架构总览

> 面向"想读懂/改代码"的人。按**数据在流水线里怎么流**讲，不按目录树讲。
> ⭐ 核心一句话：**`cv::Mat`（原图）→ `Armor`（装甲板）→ `Target`（整车）→ `Plan`（云台指令）→ 串口/CAN。**

---

## 1. 五层架构

| 层 | 目录 | 规模 | 职责 | 能碰硬件吗 |
|---|---|---|---|---|
| **入口层** | `src/` | 2343 行 | 4 个兵种主循环 + CLI + 线程编排 | ✅ 只有它能 |
| **算法层** | `core/` | 9589 行 | 自瞄/打符的全部算法 | ❌ **纯计算，零硬件依赖** |
| **IO 层** | `io/` | 2832 行 | 相机抽象 + 下位机协议 | ✅ 串口/CAN/ROS2 |
| **驱动层** | `drivers/` | 1377 行 | 具体相机 SDK（海康/MV/USB）+ IMU | ✅ 厂商 SDK |
| **工具层** | `utils/` | 7284 行 | 日志 / 调试 / YAML / 数学 / 并发 / 可视化 | ❌ |

⭐ **分层的实际意义**：`core/` 可以在**没有相机、没有下位机**的情况下单独测试
（`test/function/` 里 22 个 ctest 就是这么跑的）。

## 2. 自瞄流水线（最核心的部分）

```
┌─────────────────────────────────────────────────────────────────┐
│ 相机 (drivers/ + io/camera/)                                     │
│   cv::Mat  1440×1080  +  时间戳 t                                │
└────────────────────────┬────────────────────────────────────────┘
                         │
                         ▼  ① 识别器 ── core/auto_aim/detector/
┌─────────────────────────────────────────────────────────────────┐
│ DetectorSlot（统一入口，内部两个实现可切换）                       │
│   · YOLO（默认）—— yolov5 / yolov8 / yolo11 三个模型              │
│   · traditional（传统视觉，备用）                                  │
│                                                                  │
│ 输出：std::list<Armor>                                            │
│   Armor = 装甲板：4 个角点 points + 颜色 color + 编号 name         │
│                   + 类型 type(big/small) + 置信度 confidence      │
└────────────────────────┬────────────────────────────────────────┘
                         │
                         ▼  ② 解算器 ── core/auto_aim/solver/
┌─────────────────────────────────────────────────────────────────┐
│ Solver.cppn（PnP）—— 像素 → 3D                                    │
│   ⚠️ 依赖云台姿态：set_R_gimbal2world(q) 每帧喂四元数              │
│                                                                  │
│ 作用：把 Armor 的 2D 角点解成「这个装甲板在空间中的位姿」           │
│ 输出：Armor 里被填上 xyz_in_world / ypr（世界坐标）                │
│ 副产物：reproj_err（重投影误差）—— ⭐ 质量指标，>100px 会告警      │
└────────────────────────┬────────────────────────────────────────┘
                         │
                         ▼  ③ 跟踪器 ── core/auto_aim/tracker/
┌─────────────────────────────────────────────────────────────────┐
│ Tracker（状态机）                                                 │
│   ├─ ArmorFilter   5 条射击过滤规则（颜色/无敌/编号/集火/优先级）   │
│   ├─ ArmorPriority 4 个 PriorityMap（排序/切换用）                 │
│   ├─ Voter         多帧投票（去抖动）                             │
│   ├─ nav_bridge    ⭐ 导航桥上行（哨兵：目标信息发给导航）          │
│   └─ Target        ⭐ EKF 本体（core/auto_aim/target/）           │
│                                                                  │
│ EKF 状态 x = [x vx y vy z vz a w r l h]（11 维）                  │
│   x,y,z 位置 · vx,vy,vz 速度 · a 朝向 · w 角速度 · r,l,h 半径     │
│                                                                  │
│ 状态机：lost → detecting → tracking → temp_lost（可回 tracking）  │
│ 输出：std::list<Target>                                           │
│   ⭐ 关键能力：predict(t) —— 预测【未来 t 时刻】装甲板在哪         │
│      → 这就是"打提前量"的来源                                     │
│                                                                  │
│ ⚠️ 数字分类不在 Tracker 里 —— 是**独立模块**                       │
│    core/auto_aim/classifier/（检测后立即调用，DNN/OpenVINO 两后端）│
└────────────────────────┬────────────────────────────────────────┘
                         │
                         ▼  ④ 规划器 ── core/auto_aim/planner/
┌─────────────────────────────────────────────────────────────────┐
│ 两条路线（哨兵/步兵现在都用 MPC）：                                │
│   · Planner (mpc.cpp)     ⭐ MPC —— 预测 + 轨迹规划 + 前馈        │
│   · Aimer   (legacy.cpp)  传统 —— 直接解算 + 延时补偿（同济哨兵）  │
│                                                                  │
│ Planner 内部：                                                    │
│   ① 取最近装甲板 → 算弹道（Trajectory）→ 得到飞行时间 t_fly        │
│   ② target.predict(t_fly) —— 预测弹丸到达时目标在哪                │
│   ③ 两个 tinympc 求解器（yaw 一个、pitch 一个）解出云台轨迹        │
│      代价 Q/R 可配 · max_iter=10 · HORIZON=100                    │
│   ④ 判据：traj_err < fire_thresh ⇒ 可以开火                       │
│                                                                  │
│ 输出：Plan { control, fire, yaw, yaw_vel, yaw_acc,               │
│              pitch, pitch_vel, pitch_acc, + 调试量 }              │
│   ⭐ vel/acc 是 MPC 的"前馈"—— 让云台提前发力，减少滞后            │
└────────────────────────┬────────────────────────────────────────┘
                         │
                         │
                         │  ⚠️ 另有【独立的开火判据模块】core/auto_aim/shooter/
                         │     （角度容差 + 距离阈值，与 MPC 的 traj_err 判据并存）
                         ▼  ⑤ 下位机 ── io/board/
┌─────────────────────────────────────────────────────────────────┐
│ 三种链路（按兵种）：                                               │
│   · io::Gimbal       串口 + CRC16      ← 步兵 / 英雄              │
│   · io::SentrySerial 串口 + 0xBB66尾   ← 哨兵（46/42 字节）       │
│   · io::CBoard       CAN               ← 无人机                  │
│   （录像时用 ReplayBoard / ReplayBoard 替身）                     │
└─────────────────────────────────────────────────────────────────┘
```

## 3. 数据是怎么"变形"的（一张表看懂）

| 阶段 | 输入 | 输出 | 谁产生 | 关键字段 |
|---|---|---|---|---|
| ① 识别 | `cv::Mat` | `list<Armor>` | `DetectorSlot` | `points` / `color` / `name` / `type` / `confidence` |
| ② 解算 | `Armor`（2D） | `Armor`（含 3D） | `Solver` | `xyz_in_world` / `ypr` / `reproj_err` |
| ③ 跟踪 | `list<Armor>` | `list<Target>` | `Tracker` | EKF 11 维状态 + `armor_xyza_list()` |
| ④ 规划 | `Target` | `Plan` | `Planner` | `yaw/pitch` + `vel/acc` + `fire` |
| ⑤ 下发 | `Plan` | 串口/CAN 帧 | `Board` | 见 [docs/21](21-四兵种通信方式.md) |

⭐ **每一步的产物都能单独看**：`--stop-after=detect|track|plan` 可以停在任意一步，
   再用 `--debug-img` 看图 / `--csv` 拿数值 / `--log-only=xxx` 看日志。

## 4. 四个兵种怎么复用同一套流水线

⭐ **算法完全共享（`core/`），只有三处不同：**

| | infantry | hero | sentry | uav |
|---|---|---|---|---|
| **主循环** | `src/infantry.cpp` | `src/hero.cpp` | `src/sentry.cpp` | `src/uav.cpp` |
| **相机数** | 1 | 1 | 1 | 1 |
| **下位机** | 串口 `Gimbal` | 串口 `Gimbal` | ⭐ **串口 `SentrySerial`** | CAN `CBoard` |
| **规划器** | **MPC** | **MPC** | ⭐ **MPC**（W136 起） | legacy `Aimer` |
| **打符** | ✅ 有 | ✅ 有 | ❌ 无 | ✅ 有 |
| **ROS2** | ❌ | ❌ | ⭐ 有（导航桥） | ❌ |
| **特殊** | — | 42mm 弹速 | 单枪口 · 无敌/集火指令 | 独立 DM_IMU |

⭐⭐ **关键设计：主循环写成【模板】**
```cpp
template <typename Board>
int run_sentry(io::CameraBase & camera, Board & cboard, ...);
// 实例化两次：run_sentry<SentryBoard> / run_sentry<ReplayBoard>
```
⇒ ⭐ **有硬件走真板卡，没硬件走录像替身，业务逻辑一份代码**
（`ReplayBoard` 刻意模仿 `SentryBoard` 的公开形状 —— 这是本项目反复用的手法）

## 5. "槽位模式" —— 可替换的实现

⭐ 凡是有多种做法的环节，都做成**接口 + 运行时选择**（而不是 `#ifdef`）：

| 环节 | 接口 | 实现 | 怎么选 |
|---|---|---|---|
| **识别器** | `DetectorSlot` | `YOLO` / `traditional` | yaml `detector_impl` |
| **弹道** | `ITrajectory` | `ideal` / `rk4_drag` / `table` / `tongji_linear` | yaml `trajectory_impl` |
| **规划器** | — | `Planner`(MPC) / `Aimer`(legacy) | 各兵种主循环直接选 |
| **相机** | `CameraBase` | 海康 / MindVision / USB / 录像 | yaml `camera_config` |
| **下位机** | `IBoard` 或模板 | 串口 / CAN / 虚拟 / 录像 | CLI + yaml |

⭐ **好处**：加一个新实现**不用改调用方**，且能在同一台机器上 A/B 对比
（`docs/20` 的运行效率对比就是这么做的）。

## 7. 调试体系（三层，与算法解耦）

| 层 | 手段 | 成本 | 看什么 |
|---|---|---|---|
| **L0/L1 概览** | `logger()->debug(...)` + 热键 `d` | 运行时级别过滤 | 每帧一行"识别到了啥" |
| **L2 数值** | `FrameDebug` → **58 列 CSV** / PlotJuggler | 每帧一次结构体拷贝 | ⭐ 离线分析（`tools/csv_viewer.html`） |
| **L3 图像** | `--debug-img` / `--debug-window` | ⭐ **`wants_image()` 门控 ⇒ 不看图零开销** | 绿框/淡蓝预测/红瞄准点 |
| **细节** | `LOG_XXX(...)` **编译期宏**（11 个） | 关掉时**整条语句连参数消失**（1.65 ns vs 89 ns） | 逐帧的算法内部量 |

⭐ **判据**：关掉后**会让人误判"功能坏了"吗**？会 ⇒ 走运行期；不会 ⇒ 走编译期宏。
详见 `core/debug.hpp`（按场景导航的开关总控）。

## 8. 线程模型

⭐ **只有步兵/英雄/哨兵有 plan 线程**（uav 是单线程）：

```
主线程                                     plan 线程（100 Hz）
  ├─ camera.read()         阻塞
  ├─ imu_at(t) → 四元数                    ┌──────────────────┐
  ├─ solver.set_R_gimbal2world(q)          │ try_peek(target) │←─ target_queue(1)
  ├─ yolo.detect()     ~6 ms               │ planner.plan()   │   ⭐ "最新值槽位"
  ├─ tracker.track()   ~0.4 ms             │ board.send()     │
  ├─ target_queue.push(target) ────────────┤ sleep(10ms)      │
  └─ hub.on_frame(fd) / overlay            └──────────────────┘
```

⭐ **为什么要独立线程**：MPC 的价值在**预测 + `vel/acc` 前馈**，
   若同步跑在主循环里，控制频率 = 帧率（~30 Hz），前馈优势体现不出来。
   放线程里 ⇒ **云台 100 Hz 更新，与感知解耦**。

⚠️ **代价**：`board.send()` 会被两个线程访问 ⇒ `SentrySerial::send()` 已加锁
（`tx_mutex_`）；`psnap` 用 `std::mutex` 保护。
