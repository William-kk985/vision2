# 四兵种通信方式

> 本文记录四个兵种与下位机/导航之间的通信链路、协议与配置。
> ⭐ 结论：**与同济上游完全一致**（步兵/英雄走串口，哨兵/无人机走 CAN，仅哨兵接 ROS2）。

---

## 1. 总览

| 兵种 | 下行（视觉 → 下位机） | 上行（下位机 → 视觉） | ROS2 桥 | 姿态来源 |
|---|---|---|---|---|
| `infantry` | **串口** `io::Gimbal` | 串口（同链路双向） | ❌ | 串口四元数 |
| `hero` | **串口** `io::Gimbal` | 串口 | ❌ | 串口四元数 |
| `sentry` | **CAN** `io::CBoard` ⚠️（串口方案已就绪，见 §8） | CAN | ⭐ **有** | CAN 四元数 |
| `uav` | **CAN** `io::CBoard` | CAN | ❌ | CAN 四元数 + **独立 DM_IMU 串口** |

**代码入口**：

| 兵种 | board 创建处 |
|---|---|
| `infantry` | `src/infantry.cpp` → `io::make_board(...)`（W54 自动感应） |
| `hero` | `src/hero.cpp` → `io::make_board(...)` |
| `sentry` | `src/sentry.cpp` → `io::CBoard`（模板参数，录像时用 `ReplayCBoard`） |
| `uav` | `src/uav.cpp` → `io::CBoard`（同上） |

⭐ **上游对照**（`vision_v2/upstream/sp_vision_25/src/`）：
`standard_mpc.cpp` 用 `io::Gimbal` · `sentry_multithread.cpp` 用 `io::CBoard` + `io::ROS2` · `uav.cpp` 用 `io::CBoard`
⇒ **一致**。

## 2. 串口链路（infantry / hero）—— `io::Gimbal`

### 2.1 配置

```yaml
# params/robots/infantry.yaml（hero 同）
com_port: "/dev/gimbal"
```

### 2.2 帧格式（`io/board/gimbal/gimbal.hpp`）

⭐ **两个固定长度、`__attribute__((packed))` 的结构体，均 `static_assert(sizeof(...) <= 64)`，带 CRC16。**

**下行 `VisionToGimbal`**：
```cpp
uint8_t  head[2] = {'S','P'};   // 帧头
uint8_t  mode;                  // 0=不控制 1=控制云台不开火 2=控制云台且开火
float    yaw, yaw_vel, yaw_acc; // ⭐ 含前馈（vel/acc）—— 同济 MPC 需要
float    pitch, pitch_vel, pitch_acc;
uint16_t crc16;
```

**上行 `GimbalToVision`**：
```cpp
uint8_t  head[2] = {'S','P'};
uint8_t  mode;                  // 0=空闲 1=自瞄 2=小符 3=大符
float    q[4];                  // ⭐ wxyz 顺序四元数（云台姿态）
float    yaw, yaw_vel, pitch, pitch_vel;
float    bullet_speed;
uint16_t bullet_count;          // 子弹累计发送次数
uint16_t crc16;
```

### 2.3 关键行为

- ⭐ **同一个串口双向**：`read_thread` 后台收上行，`send()` 写下行
- ⚠️ **掉线重连**：打不开串口时**每 100 ms 重试**（首条 + 每 50 次各报一次日志，W109 降噪）
- ⚠️ **没插硬件**：`make_board` 自动降级 `VirtualBoard` + 警告（见 §5）

## 3. CAN 链路（sentry / uav）—— `io::CBoard`

### 3.1 配置

```yaml
# params/robots/sentry.yaml
quaternion_canid: 0x01        # ⭐ 上行：四元数
bullet_speed_canid: 0x110     # ⭐ 上行：弹速 + 档位
send_canid: 0xff              # ⭐ 下行
can_interface: "can0"

# params/robots/uav.yaml
quaternion_canid: 0x001       # ⚠️ 与哨兵不同
bullet_speed_canid: 0x110
send_canid: 0xff
can_interface: "can0"
```

⚠️ **注意 CAN ID 各兵种不同**（`sentry` 用 `0x01`，`uav` 用 `0x001`）。
⚠️ `infantry.yaml` / `hero.yaml` 里**也有**这套 CAN 配置，但两者**实际走串口**，该段不生效。

### 3.2 帧格式（`io/board/can/cboard.cpp` 的 `callback`）

⭐ **上行帧按 CAN ID 区分**（`SocketCAN` 收到后在 `callback` 里分派）：

| CAN ID | 字段 | 编码 |
|---|---|---|
| `quaternion_canid` | `x, y, z, w` | `int16` 大端 ÷ 1e4；⚠️ **校验 `|q|²-1| < 1e-2`**，不合法则 warn 并丢弃 |
| `bullet_speed_canid` | `bullet_speed` | `int16` 大端 ÷ 1e2 |
| | `mode` | `uint8`（档位） |
| | `shoot_mode` | `uint8`（哨兵左/右/双枪口） |
| | `ft_angle` | `int16` 大端 ÷ 1e4（摩擦轮角度） |

⭐ **下行**（`send_canid`，`can_dlc = 8`，**单帧 8 字节**）：
```
data[0]          = control              (uint8, 0/1)
data[1]          = shoot                (uint8, 0/1)
data[2..3]       = yaw   × 1e4          (int16 大端)
data[4..5]       = pitch × 1e4          (int16 大端)
data[6..7]       = horizon_distance×1e4 (int16 大端；⚠️ 无人机专有字段)
```
⚠️ 注意：**yaw/pitch 之外还发 `horizon_distance`** —— 这是 `io::Command` 里**无人机专有**的字段。

### 3.3 ⚠️ 与 `io::Gimbal` 的接口差异（W31 记录）

| | `io::Gimbal` | `io::CBoard` |
|---|---|---|
| 下发 | `send(8 个标量)` | `send(io::Command)` |
| 姿态 | `q(t)`（四元数队列） | `imu_at(t)` |
| 档位 | `mode()`（`GimbalMode`） | 公开成员 `Mode mode` + `ShootMode shoot_mode` |

⭐ **不为了统一而改 `CBoard`** —— 而是把主循环写成**模板**，让两种下位机各实例化一次。

## 4. ROS2 链路（仅 sentry）—— 导航桥

⭐ **只有哨兵接 ROS2**（与同济一致）。启动日志：
```
[sentry] ROS2 导航桥已启动（上行 auto_aim_target_pos / 下行 enemy_status+autoaim_target）
```

### 4.1 下行（导航 → 视觉）—— `io/ros2/subscribe2nav.cpp`

| 话题消息 | 用途 | 接到哪 |
|---|---|---|
| `sp_msgs::msg::EnemyStatusMsg` | ⭐ **无敌状态**（哪些编号处于无敌） | `tracker.set_invincible(InvincibleMask)` |
| `sp_msgs::msg::AutoaimTargetMsg` | ⭐ **集火指令**（上级指定打谁） | `tracker.set_auto_aim_targets(...)` |

### 4.2 上行（视觉 → 导航）—— `io/ros2/publish2nav.cpp`

| 话题 | 消息类型 | 内容 |
|---|---|---|
| `auto_aim_target_pos` | `std_msgs::msg::String` | ⭐ **目标位置**（供导航决策） |

### 4.3 ⚠️ 依赖 `source` 工作空间

⚠️ **不 `source ros2_ws/install/setup.bash` 时，`sp_msgs` 的消息类型未注册**
⇒ `create_subscription` 抛 `rclcpp::exceptions::RCLError: type_support is null`。

⭐ **本项目 W108 已加 `try/catch`**：不再崩溃，而是报出可操作的错误并返回。

## 5. 无硬件时的自动降级 —— `io::make_board`（W54）

⭐ **infantry / hero 共用**（sentry / uav 直接建 `CBoard`，不降级）。

| `--no-board` | `com_port` 存在 | `--strict-board` | 结果 |
|---|---|---|---|
| 是 | — | — | ⭐ `VirtualBoard`（显式要求无板） |
| 否 | ✅ | — | `Gimbal`（真下位机） |
| 否 | ❌ | 否 | ⭐ **`VirtualBoard` + 大声警告**（默认降级） |
| 否 | ❌ | **是** | ❌ **报错退出**（= 同济行为） |

⭐ **默认降级的理由**：没接硬件是**开发机的常态**，直接崩体验差。
⚠️ **比赛用 `--strict-board`** —— "宁可失败也不要静默跑错"。

## 6. 无人机的额外串口 —— DM_IMU

⭐ **`uav` 除 CAN 外，还有一条独立的 IMU 串口**（`drivers/dm_imu/`）：

```cpp
serial_.setBaudrate(921600);   // ⚠️ 全项目唯一显式设波特率的地方
```

⭐ **用途**：无人机需要更高频率/更低延迟的姿态，不复用 CAN 上的四元数。

## 7. 录像模式：不通信

⭐ **录像模式用 `ReplayBoard`（infantry/hero）或 `ReplayCBoard`（sentry/uav）**：

| | 是什么 |
|---|---|
| `io::ReplayBoard` | 复用 `io::ReplayBoard`（`io/board/replay.hpp`），从 `demo.txt` 回放四元数，`send()` 只记录不发送 |
| `ReplayCBoard` | ⭐ **定义在各自主循环里**，**刻意模仿 `io::CBoard` 的公开形状**（`mode` / `bullet_speed` / `shoot_mode` / `imu_at` / `send(Command)`）⇒ 主循环模板**一份逻辑两种下位机** |

⚠️ **录像模式下的固有限制**：云台是"死的"（只回放录制的四元数，不真转）
⇒ ⭐ 这会导致"用当前云台姿态投影未来瞄准点"失效（见 [docs/20](20-运行效率对比-改造架构vs同济.md) 与 W117）。

### 8.0 ⭐⭐⭐ 哨兵只走串口（W135 —— 已定稿）

⭐ **按 2026-10 的决定**，哨兵链路**只保留串口**，已移除全部"多兼容"：

| ❌ 已移除 | 说明 |
|---|---|
| **CAN 链路** | `sentry.cpp` 不再 include/使用 `io::CBoard` |
| **`--board` 开关** | 不再需要选链路 ⇒ **没有这个参数了** |
| **`shoot_mode` / `--shoot-mode`** | ⭐ **本项目哨兵是单枪口**；`aimer.aim()` 直接传常量 `io::ShootMode::both_shoot` |
| **`--no-board` / `--strict-board`** | ⚠️ 这两个参数**只被 `make_board`（步兵/英雄）使用** —— 哨兵里的定义是**无效配置**，一并删除 |

⭐ **保留**：
· **`SentryBoard`**（真实串口，`io::SentrySerial` 的薄封装，提供主循环要的形状）
· **`ReplayBoard`**（录像替身）—— ⚠️ **录像回放是没硬件时唯一的调试手段，不是"多兼容"**
· ⚠️ **`io::CBoard` 与 `io::ShootMode` 类型本身** —— `uav.cpp` 仍在用，
  且 `Aimer::aim()` 的签名要求 `ShootMode` 参数（**不为了哨兵去改共享代码**）

```bash
src/sentry params/robots/sentry.yaml                     # ⭐ 真实硬件（串口）
src/sentry --video=<录像> params/robots/sentry.yaml      # ⭐ 录像回放
```

#### 主循环的 board 形状（模板的两个实例化）

| 依赖 | `SentryBoard` | `ReplayBoard` |
|---|---|---|
| `double bullet_speed` | `imu_at()` 时从 `state()` 同步 | 构造时给定 |
| `io::Mode mode` | 从 `serial.mode()` 映射 | 构造时给定 |
| `imu_at(t)` | 转发 `serial.q(t)`（slerp） | 转发 `replay_.q(t)` |
| `send(io::Command)` | 拆包 → `serial.send(...)` | 只记日志 |

#### ⭐ 哨兵用 `Aimer`（legacy）而**不是** `Planner`（MPC）—— 故 CSV 里 `pln_*` 全 0

⭐ 与同济一致（`upstream/src/sentry_multithread.cpp:59` 也是 `auto_aim::Aimer`）。
⇒ ⭐ **CSV 里 `pln_*` / `sht_*` 全 0 是既有设计**，不是缺陷。

⭐ **`--board=can|serial`**（默认 **`can`**，保持原行为）：

```bash
src/sentry params/robots/sentry.yaml                    # ⭐ 默认走 CAN（io::CBoard）
src/sentry --board=serial params/robots/sentry.yaml     # ⭐ 走串口（io::SentrySerial）
```

⭐ **实现方式**：新增适配类 **`SentrySerialBoard`**（在 `src/sentry.cpp` 内），
**刻意模仿 `io::CBoard` 的公开形状**（与 `ReplayCBoard` 同一先例）⇒
主循环模板 `run_sentry<Board>` **一份逻辑三种下位机**：

| 模板依赖的成员 | `SentrySerialBoard` 怎么给 |
|---|---|
| `double bullet_speed` | 每次 `imu_at()` 时从 `state().bullet_speed` 同步 |
| `io::Mode mode` | 从 `serial.mode()` 映射（串口协议无 `outpost`） |
| `io::ShootMode shoot_mode` | ⭐ **恒为 `both_shoot`**（见下） |
| `Eigen::Quaterniond imu_at(t)` | 转发 `serial.q(t)`（slerp 插值） |
| `void send(io::Command)` | 拆包 → `serial.send(control, shoot, yaw, 0,0, pitch, 0,0)` |

#### ⭐ `shoot_mode` 固定 `both_shoot` —— 因为**本项目哨兵是单枪口**

⚠️ **与同济的左/右/双枪口不同。** `shoot_mode` 唯一的功能用途是左右枪口偏置：
```cpp
// core/auto_aim/planner/legacy.cpp:160-162
if (shoot_mode == left_shoot  && left_yaw_offset_.has_value())  yaw += ...;
else if (shoot_mode == right_shoot && right_yaw_offset_.has_value()) yaw += ...;
```
⇒ ⭐ **传 `both_shoot` 两个分支都不命中 ⇒ 不加偏置**，正是单枪口所需。

⚠️ **串口 46 字节上行包里本来就没有 `shoot_mode` 字段** —— 这与单枪口一致，**非缺陷**。

### 8.1 与 `io::Gimbal`（步兵/英雄）的差异

| | `io::Gimbal` | `io::SentrySerial` |
|---|---|---|
| **帧尾** | ⚠️ **CRC16** | ⭐ **固定 `0xBB 0x66`** |
| **下行长度** | ≤64 字节 | **42 字节** |
| **上行长度** | ≤64 字节 | **46 字节** |
| **上行额外字段** | ❌ | ⭐ **`health` / `game_state`** |
| **下行额外字段** | ❌ | ⭐ **`nav_x` / `nav_y` / `nav_w` / `status_position`** |
| **波特率** | serial 库默认 | ⭐ **115200**（协议约定） |

### 8.2 上行 `SentryToVisionPacket`（46 字节）

```
0x00 head[2]         "SP"                        0x23 bullet_speed  float  m/s
0x02 mode            uint8 0:idle 1:auto_aim     0x27 bullet_count  uint16
                          2:small_buff 3:big_buff 0x29 health        uint16  ⭐
0x03 q[4]            float[4] 四元数 wxyz         0x2B game_state    uint8   ⭐
0x13 yaw             float  rad                   0x2C tail[2]       0xBB 0x66
0x17 yaw_vel         float  rad/s
0x1B pitch           float  rad
0x1F pitch_vel       float  rad/s
```
⭐ Python `struct` 格式串 `<2sB9fHHB2s`

### 8.3 下行 `VisionToSentryPacket`（42 字节）

```
0x00 head[2]           "SP"                      0x1B nav_x           float  m    ⭐
0x02 mode              uint8 0:no_ctrl           0x1F nav_y           float  m    ⭐
                             1:ctrl 2:ctrl+fire   0x23 nav_w           float  rad  ⭐
0x03 yaw               float  rad                0x27 status_position uint8  预留
0x07 yaw_vel           float  rad/s              0x28 tail[2]         0xBB 0x66
0x0B yaw_acc           float  rad/s^2
0x0F pitch             float  rad
0x13 pitch_vel         float  rad/s
0x17 pitch_acc         float  rad/s^2
```
⭐ Python `<2sB9fB2s`

### 8.4 ⚠️ 与参考实现（旧版赫兹 `src/drivers/sentry_serial/`）的差异

| 项 | 参考实现 | 本实现 | 理由 |
|---|---|---|---|
| **帧格式** | — | ⭐ **逐字节相同** | 必须与下位机一致，**不可改** |
| **波特率** | 115200 | 115200 | 同 |
| **yaw/pitch 偏置** | ⚠️ **硬编码 −1.8° / −6.6°** | ⭐ **读 yaml**（缺省 0） | 标定值不应埋在代码里 |
| **串口缺失** | ⚠️ 仅 `error` 一行 | ⭐ 报**可操作的**错误（列出机器可用串口）+ **不 `exit`** | 沿用本项目 W53 / `make_board` 的哲学 |

### 8.5 ⭐⭐ 导航数据可缺省 —— 没有导航时这一帧【照发】

⭐ **本帧与导航【无关】的字段永远有效**：`mode` / `yaw{,_vel,_acc}` / `pitch{,_vel,_acc}`
⇒ ⭐ **云台控制不依赖导航包**，`nav_*` 缺失时照常下发（哨兵能独立工作的前提）。

| 场景 | `nav_x` / `nav_y` / `nav_w` | `status_position` |
|---|---|---|
| ⭐ **导航包未移植/未就绪** | ⭐ **全部 0** | ⭐ **用它发"别的信息"** |
| ⭐ **导航包已就绪** | 填入真实导航数据 | 按需（默认 0） |

#### ⭐ `status_position` = **导航状态码**（约定已存在）

⭐ **来源**：导航脚本 `scripts/nav/sentry_nav_cartographer.py` 通过 ROS2 话题
**`/sentry/nav_status`**（`std_msgs::msg::UInt8`）发布 ⇒ 视觉侧**订阅后原样转发**，
**不自己编码**。

⭐ **编码表**（三处逐字一致：导航脚本 `:112-114` 注释、旧版赫兹
`src/drivers/ros2/subscribe2nav.cpp` 的 `status_meaning[]`）：

| 值 | 含义 |
|---|---|
| `0` | 残血回血中（HOME 点，血量 150~349） |
| `1` | R1↔R2 或 B1↔B2 移动（正常巡逻） |
| `2` | R2↔R3 / B2↔B3 移动，**或** HOME 回血中（**也用于"识别到目标"**） |
| `3` | 残血撤退中（血量 &lt;150） |
| ⭐ **`4`** | ⭐ **无导航 / 待机** |

⚠️⚠️ **关键：**"没有导航"时的值是 **`4`**，**不是 `0`**（`0` 是"残血回血中"）。

#### ⭐⭐ 当前决定（2026-10）：`status_position` **一直发 `0`**

⭐ 常量：**`io::SENTRY_STATUS_FIXED = 0`**（改一行即可调整）

### 8.6 ⭐⭐ 串口设备名自适应（`io/board/serial_scan.hpp`）

⚠️ **问题**：USB 转串口按**插入顺序**枚举 ⇒ 今天 `/dev/ttyUSB0`、明天可能是 `ttyUSB1`；
换 USB 口或同时插调试线都会变名。

#### ⭐ 原则：**确定性优先，绝不静默选错设备**

⚠️ **选错串口比选不到更糟** —— 会往错误的设备写数据，且**不会报错**。

| 情形 | 行为 |
|---|---|
| yaml 给具体路径且设备存在 | ⭐ 直接用（比赛要确定性） |
| yaml 给具体路径但设备**不存在** | ⚠️ 报错 + 列出可用串口，⭐ **不自动换** |
| yaml 为空 / 写 `"auto"` | ⭐ 自适应扫描 |

#### 自适应匹配规则（按可靠性降序）

| 规则 | 依据 | 可靠性 |
|---|---|---|
| ① **序列号** | `/sys/class/tty/<dev>/device/serial` | ⭐⭐⭐ 最可靠（需下位机烧录固定序列号） |
| ② **VID:PID** | `.../idVendor` + `idProduct` | ⭐⭐ 可靠（如 CH340 = `1a86:7523`） |
| ③ **子串** | `manufacturer` / `product` / `driver` | ⭐ 一般 |
| ④ **唯一候选** | 只有一个串口 | ⭐ 可用（多设备时不生效） |
| ⑤ 多候选且无规则命中 | — | ⚠️ **报错列出全部，不猜** |

#### yaml 配置

```yaml
serial_port: "auto"         # 或留空；给具体路径则严格使用该路径
serial_serial_no: ""        # ① 序列号（最可靠）
serial_vid_pid: ""          # ② "VID:PID"
serial_match: ""            # ③ 厂商/产品/驱动子串
```

⭐⭐ **当前决定（2026-10）：写死设备路径** —— `serial_port: "/dev/sentry"`，**不用自适应**。
⭐ 建议配 **udev 规则**把下位机固定成这个名字（唯一完全确定的方案）。

⭐ **自适应能力保留在代码里**（`io/board/serial_scan.hpp`）但**默认不用**；
   需要时把 `serial_port` 改成 `"auto"` 即可启用。

⚠️ **开发机（无 USB 串口）上自适应会失败并给出提示** —— 这是**预期行为**，不是 bug。

### 8.7 ⭐ 协议契约的自动化保障

`test/function/test_sentry_protocol.cpp`（**58 项，全部通过**）：
- ⭐ **总长度**：46 / 42
- ⭐ **逐字段 `offsetof`**（比只查总长度强：**总长度对而顺序错是可能的**，例如两个相邻 float 互换）
- ⭐ **帧头/帧尾常量** + **打包字节序**（实测 `1.0f` → `00 00 80 3F`）

- ⭐ **状态位固定值**（`SENTRY_STATUS_FIXED == 0`）+ ⭐ **显式断言"固定 0 ≠ 约定的无导航值 4"**
- ⭐ **串口自适应匹配**（5 条规则的优先级 + "多候选不猜" + 空列表 + `vid_pid()` 健壮性）

⚠️ 收发错位是**静默**的（读到的 `q`/`yaw` 全是垃圾但不报错）⇒ 该单测是**唯一防线**。

## 9. ⭐⭐⭐ 哨兵通信的当前架构（W135 定稿）

> 本节是**现状快照** —— 讲清"代码怎么分层、数据怎么流、谁在什么线程"。

### 9.1 三层结构

```
┌─────────────────────────────────────────────────────────────────┐
│ ① src/sentry.cpp 的 SentryBoard（适配层，~45 行）                 │
│    给主循环提供统一形状：                                          │
│      double bullet_speed · io::Mode mode · size_t sent_count      │
│      imu_at(t) → 四元数      send(8 标量)                          │
│    ⭐ 为什么要有它：主循环写成模板 ⇒ 真实串口 / 录像替身同一份逻辑   │
├─────────────────────────────────────────────────────────────────┤
│ ② io/board/sentry_serial/（协议 + 驱动，663 行）                   │
│    · SentryToVisionPacket  46 B（上行）                           │
│    · VisionToSentryPacket  42 B（下行）                           │
│    · SentrySerial          读线程 + send + 重连 + q(t) slerp      │
├─────────────────────────────────────────────────────────────────┤
│ ③ io/board/serial_scan.hpp（设备选择，199 行）                     │
│    写死 /dev/sentry（⚠️ 不存在就报错，不自动换）                    │
│    ⭐ 自适应能力保留但默认关（5 条匹配规则）                        │
└─────────────────────────────────────────────────────────────────┘
```

### 9.2 调用链（主循环一侧）

```
主线程                                     plan 线程（100 Hz）
  │                                          │
  ├─ cboard.imu_at(t - 1ms)                  ├─ planner.plan(target, cboard.bullet_speed)
  │    ├─ serial.state()      ← mutex_       │      └─ MPC：Target → Plan
  │    ├─ bullet_speed = st.bullet_speed     └─ cboard.send(
  │    ├─ mode = to_mode(serial.mode())             plan.control, plan.fire,
  │    └─ return serial.q(t)  ← mutex_（slerp）     plan.yaw, plan.yaw_vel, plan.yaw_acc,
  │                                                  plan.pitch, plan.pitch_vel, plan.pitch_acc)
  ├─ plan_mode = cboard.mode                          └─ serial.send(...)  ← tx_mutex_
  │
  └─ 非自瞄档时 plan 线程发 (false,false,0×6)
```

⭐ **关键设计**：**感知（30 Hz）与下发（100 Hz）解耦** —— MPC 的 `vel/acc` 前馈才有意义。

### 9.3 线程与锁

| 线程 | 干什么 | 用哪把锁 |
|---|---|---|
| **主线程** | 感知 | `mutex_`（读 `state()` / `mode()` / `q()`） |
| **plan 线程** | 100 Hz 规划 + 下发 | `tx_mutex_`（写 `tx_data_` + `serial_.write`） |
| **`read_thread`**（`SentrySerial` 内部常驻） | 逐字节收帧 | `mutex_`（写 `rx_data_` / `state_` / `mode_`）+ `queue_`（自带锁） |

⭐ **`tx_mutex_` 是 W136 加锁的** —— plan 线程引入后，`send()` 与 `read_thread` 会并发。

⚠️ **已知的弱同步点**：`SentryBoard::bullet_speed` / `mode` 是**普通成员**（非 `atomic`），
   plan 线程读、主线程写 ⇒ **严格说是 data race**。
   ⭐ 实践上：x86-64 的 8 字节对齐读写本身原子，**不会撕裂**；且 `bullet_speed` 只影响弹道积分，
   偶发读到上一帧的值无实质影响。📌 若要严谨，可改为 `std::atomic<double>`。

### 9.4 协议（回顾）

```
帧头 "SP" (0x53 0x50)      帧尾 0xBB 0x66      ⚠️ 不是 CRC16
```
**上行 46 B**（下位机 → 视觉）：`mode` · **`q[4]`（四元数，下位机发）** · `yaw/yaw_vel/pitch/pitch_vel`
· `bullet_speed` · `bullet_count` · `health` · `game_state`
**下行 42 B**（视觉 → 下位机）：`mode` · `yaw/yaw_vel/yaw_acc` · `pitch/pitch_vel/pitch_acc`
· **`nav_x/y/w`（发 0，待导航包）** · **`status_position`（固定 0）**

⭐ **完整偏移表见 §8.2 / §8.3**

## 11. ⭐⭐⭐ 协议字段的语义（每个字段"为什么需要"）

> 只列"是什么"没用 —— 下面**每个字段都给出：谁填 · 谁读 · 干什么**。

### 11.1 核心心智模型：这是一个**闭环控制**

```
        ┌──────────────── 视觉（上位机）───────────────┐
        │  看到目标 → 算出「云台该转到哪」→ 下发指令      │
        └───────┬──────────────────────────▲───────────┘
   下行 42 B    │                          │   上行 46 B
   「往哪转」    ▼                          │   「现在在哪 + 能不能打」
        ┌──────────────── 下位机（STM32）───────────────┐
        │  读指令 → 驱动电机 → 回传姿态/状态              │
        └──────────────────────────────────────────────┘
```
⭐ **视觉要算"提前量"，所以必须知道两件事**：
1. **云台现在在哪**（否则不知道相对角度）—— 来自上行 `q[4]` / `yaw` / `pitch`
2. **弹丸飞多久**（决定提前多少）—— 来自上行 `bullet_speed`

---

### 11.2 上行 46 B（下位机 → 视觉）逐字段

| 偏移 | 字段 | 类型 | ⭐ 谁填 · 视觉读它干什么 |
|---|---|---|---|
| `0x00` | `head[2]` | `"SP"` | 帧同步（逐字节找 `'S','P'`） |
| `0x02` | `mode` | `uint8` | 下位机填 → ⭐ **决定视觉"干不干活"**<br>`0`=idle `1`=auto_aim `2`=small_buff `3`=big_buff<br>⚠️ **视觉只在 `1` 时才检测/跟踪/规划** |
| `0x03` | ⭐ **`q[4]`** | `float[4]` | 下位机填 → ⭐ **云台姿态四元数（wxyz）**<br>视觉用它算 `solver.set_R_gimbal2world(q)`<br>⇒ **把像素投到世界系的基准** |
| `0x13` | `yaw` | `float` rad | 同上，标量形式（adapter 里映射成 `io::Mode`） |
| `0x17` | `yaw_vel` | `float` rad/s | ⭐ **云台转速** → 运动补偿 |
| `0x1B` | `pitch` | `float` rad | 同 `yaw` |
| `0x1F` | `pitch_vel` | `float` rad/s | 同 `yaw_vel` |
| `0x23` | ⭐ **`bullet_speed`** | `float` m/s | 下位机测（射频/摩擦轮）→ ⭐ **决定弹丸飞行时间 `t_fly`**<br>⇒ **决定提前量预测多远** |
| `0x27` | `bullet_count` | `uint16` | 累计发弹数 → 视觉可判断"是否真的打出去了" |
| `0x29` | ⭐ **`health`** | `uint16` | ⭐ **仅哨兵有** → 血量（导航决策用） |
| `0x2B` | ⭐ **`game_state`** | `uint8` | ⭐ **仅哨兵有** → 比赛状态（0=结束 1=开始） |
| `0x2C` | `tail[2]` | `0xBB 0x66` | 帧校验（⚠️ **不是 CRC16**） |

⭐ **视觉侧实际读取的位置**（`sentry_serial.cpp:312-326`）：
```cpp
q = {pkt->q[0..3]};  queue_.push({q, timestamp});   // ⭐ 带时间戳入队（供 slerp）
state_.yaw/yaw_vel/pitch/pitch_vel = ...            // 运动补偿
state_.bullet_speed = pkt->bullet_speed;            // → t_fly
state_.health / game_state = ...                    // 哨兵专有
mode_ = 从 pkt->mode 映射
```

### 11.3 下行 42 B（视觉 → 下位机）逐字段

| 偏移 | 字段 | 类型 | ⭐ 视觉从哪算出来的 · 下位机拿它干什么 |
|---|---|---|---|
| `0x00` | `head[2]` | `"SP"` | 帧同步 |
| `0x02` | `mode` | `uint8` | ⭐ **由 `control`/`fire` 编码**：<br>`!control → 0`（不控制）· `control&&!fire → 1`（控云台不开火）· `control&&fire → 2`（控制且开火） |
| `0x03` | `yaw` | `float` rad | ⭐ **MPC 解出的目标角度**（`plan.yaw` = `yaw_solver_->work->x(0, HALF_HORIZON)`）|
| `0x07` | ⭐ **`yaw_vel`** | `float` rad/s | ⭐ **MPC 的前馈**（`work->x(1, HALF_HORIZON)`）<br>⇒ **下位机可据此提前发力，减小滞后** |
| `0x0B` | ⭐ **`yaw_acc`** | `float` rad/s² | ⭐ **MPC 的控制量**（`work->u(0, HALF_HORIZON)`，受 `max_yaw_acc` 约束）|
| `0x0F` | `pitch` | `float` rad | 同 `yaw` |
| `0x13` | `pitch_vel` | `float` rad/s | 同 `yaw_vel` |
| `0x17` | `pitch_acc` | `float` rad/s² | 同 `yaw_acc` |
| `0x1B` | ⭐ **`nav_x`** | `float` m | ⚠️ **当前发 0**（导航包未移植）|
| `0x1F` | ⭐ **`nav_y`** | `float` m | ⚠️ **当前发 0** |
| `0x23` | ⭐ **`nav_w`** | `float` rad | ⚠️ **当前发 0** |
| `0x27` | ⭐ **`status_position`** | `uint8` | ⚠️ **当前固定 0**（本应是**导航状态码**，见 §8.5）|
| `0x28` | `tail[2]` | `0xBB 0x66` | 帧校验 |

### ⭐⭐ 为什么下行要发 `vel` 和 `acc`（这是 MPC 的核心价值）

⭐ **对比 `io::CBoard`（CAN，无人机用）—— 它【只发 yaw/pitch，没有 vel/acc】**：

| 字段 | `io::Gimbal`（步兵/英雄） | ⭐ **`SentrySerial`（哨兵）** | `io::CBoard`（无人机） |
|---|---|---|---|
| `yaw` / `pitch` | ✅ | ✅ | ✅（`data[2..5]`）|
| ⭐ **`yaw_vel` / `pitch_vel`** | ✅ | ✅ | ❌ **没有** |
| ⭐ **`yaw_acc` / `pitch_acc`** | ✅ | ✅ | ❌ **没有** |
| 额外 | CRC16 | `nav_x/y/w` + `status_position` | `horizon_distance` |

⭐⭐ **⇒ 这正是本项目把哨兵从 `Aimer`（legacy）换成 MPC 后【必须】发 vel/acc 的原因**：
- **位置式控制**（只发角度）：下位机用 PID 追角度，**必然滞后**
- ⭐ **前馈式控制**（角度 + 速度 + 加速度）：下位机可**提前发力** ⇒ 追踪小陀螺时滞后更小

⚠️ **而 `io::Command`（旧接口）只有 `control/shoot/yaw/pitch`** ——
   ⭐ **装不下 vel/acc** ⇒ 这就是 W136 把 `send()` 从 `send(Command)` 改成 **8 个标量**的原因。

### 11.4 一次完整交互走查（哨兵自瞄）

```
 1. 下位机 → 视觉（上行，100~500 Hz）
      mode=1(auto_aim) · q[4] · yaw=1.57 · bullet_speed=22.0 · health=380

 2. 视觉主循环（30 Hz）
      cboard.imu_at(t) → 取 q、mode、bullet_speed
      solver.set_R_gimbal2world(q)          ← ⭐ 用姿态做像素→世界系变换
      yolo.detect(img) → Armor[]            ← 检测装甲板
      tracker.track(Armor[]) → Target[]     ← EKF（内部调 solver.solve 做 PnP）
      target_queue.push(targets.front())    ← ⭐ 喂给 plan 线程

 3. plan 线程（100 Hz，与感知解耦）
      planner.plan(target, 22.0):
        trajectory->solve(22.0, d, h) → t_fly      ← ⭐ 用弹速算飞行时间
        target.predict(t_fly)                      ← ⭐ 预测弹丸到达时目标在哪
        tinympc 解 yaw/pitch 轨迹 → Plan{yaw, yaw_vel, yaw_acc, pitch, ...}
        plan.fire = traj_err < fire_thresh
      cboard.send(8 标量) → serial.send()          ← 下发

 4. 下位机（收到 42 B）
      读 yaw/yaw_vel/yaw_acc → 电机控制（含前馈）
      读 mode=2 → 扣扳机
      读 status_position → ⚠️ 当前是 0（待接导航状态码）

 5. 视觉 → 导航（ROS2，可选）
      ros2->publish(target_info_for_nav(armors, targets))
        → "x,y,1,name+1"（std_msgs::String 话题 auto_aim_target_pos）
```

### 11.5 三个"容易误解"的点

| 点 | 说明 |
|---|---|
| ⚠️ **`mode` 是双向但语义不同** | 上行 `mode` = 下位机告诉视觉"我选了什么档"；下行 `mode` = 视觉告诉下位机"我现在控制/开火" ⭐ **同一个字节名，两个方向含义不同** |
| ⚠️ **帧尾不是 CRC** | 固定 `0xBB 0x66` ⇒ **只能发现"错位"，不能发现"位翻转"**；⚠️ 弱于 `io::Gimbal` 的 CRC16 |
| ⭐ **`q[4]` 与 `yaw`/`pitch` 冗余** | 两者都传了姿态。⭐ 视觉**用 `q`**（更完整，含 roll）；`yaw`/`pitch` 供下位机侧或调试用 |
