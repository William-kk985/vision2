# 运行效率对比：改造后架构 vs 同济原版

> **测量日期**：2026-10-04
> **硬件**：x86_64 工作站 · OpenVINO 2024.6.0（CPU 推理，无 GPU）
> **素材**：`assets/demo/demo.avi`（687 帧，1440×1080，30 fps）
> **方法**：**编译同济原版代码**，编写等价 harness，同一段录像、同一机器、同一时段测量

---

## 1. 为什么不是"读代码推断"，而是"真跑一遍"

最初的对比尝试（直接跑同济的 `tests/detector_video_test`）得到 **29.2 s**，
而本项目为 **7.5 s**，看似有 3.9 倍差距。**但该结论是错的**，原因：

```cpp
// 上游 tests/detector_video_test.cpp:73
auto key = cv::waitKey(33);      // 每帧固定睡 33 ms ⇒ 687 帧 ≈ 22.7 s
line 70: plotter.plot(data);     // 另接 PlotJuggler
```

⇒ **29.2 − 22.7 ≈ 6.5 s**，与本项目属同一量级。
**因此重新编写了 harness**（`exp/bench/bench_tongji.cpp`）：
- `YOLO(config, /*debug=*/false)` —— 关闭窗口
- 无 `waitKey`、不连 PlotJuggler
- 逐段计时：`detect` / `track` / `plan`

⭐ 上游 CMake **可直接在本机配置并编译**，因此这是**真机实测**而非推算。

## 2. 分段耗时对比（中位数，单位 μs）

| 阶段 | 同济（3 次） | 本项目（5 次） | 差异 |
|---|---|---|---|
| **检测** `detect` | 5359 / 5566 / 5510 → **5510** | 5823 / 5939 / 5718 / 5842 / 5817 → **5823** | **+5.7%** |
| **跟踪** `track` | 402 / 416 / 406 → **406** | 417 / 412 / 412 / 413 / 418 → **413** | **+1.7%** |
| **规划** `plan` | 280 / 284 / 285 → **284** | 406 / 405 / 399 / 409 / 412 → **406** | **+43%** |
| **合计** | **6200** | **6642** | **+7.1%** |

**自身重复性**：两边各自的运行间波动均为 **±2%** 量级。

---

## 3. ⭐⭐ 补充测量：同线程内联（消除口径差异）

第 2 节的"规划 +43%"疑似来自**测量口径不同**（本项目在独立规划线程内计时，
同济 harness 为同线程内联）。为此新增 `exp/bench/bench_ours.cpp`：
链接本项目静态库，**同一线程内** `detect → track → plan`，与同济 harness 完全对齐。

**结果（背靠背 A/B，控制机器状态）**：

| 阶段 | 同济 | 本项目 harness（内联） | 本项目主循环（CSV） |
|---|---|---|---|
| `det` | 5510 | **7738 ~ 7969** | **5750 ~ 5759** |
| `track` | 406 | **399 ~ 404** | 426 |
| `plan` | 284 | ⭐ **272 ~ 281** | 411 |

### ⭐ 确定的结论

1. ⭐ **`plan`：内联 272~281 μs ≈ 同济 284 μs** —— **`+43%` 确系异线程测量口径所致**，
   本项目 `plan()` 本身与同济**无实质差异**（已核实求解器配置逐字相同、
   弹道槽位为纯透传）。
2. ⭐ **`track`：399~426 μs ≈ 同济 406 μs** —— 三者一致。

### ⚠️ 未能解释的分歧（必须如实说明）

⚠️ **`det` 两种测量方法给出不同结果，且可复现**：
- 内联 harness：**7738 ~ 7969 μs**
- 主循环 CSV：**5750 ~ 5759 μs**

已排除的原因：
- ⭐ `frame_count` 参数（改与不改无差别）
- ⭐ `det-stats` 开关状态（已显式对齐）
- ⭐ ROI（`use_roi: false`，两者输入均为全帧）
- ⭐ CPU 频率（实测 harness 3.6~3.8 GHz、主循环 3.3~4.0 GHz，**不足以解释 35%**）

⚠️ **因此，本项目 `detect` 相对同济的真实差异【尚无定论】**：
按主循环口径为 **+4.4%**，按内联 harness 口径为 **+41%**。
📌 **待办**：需要更严格的对照实验（如固定 CPU 频率、隔离核心、统一预热）才能定论。

## 4. 差异归因（逐条查证，不猜测）

### 4.1 检测（口径分歧，见 §3）

⭐ **计时口径已核对为等价**：两边都是 `t0 → yolo.detect() → t1`，无额外步骤。

| 本项目多的东西 | 实测开销 |
|---|---|
| `det_stats_enabled()` 检查（逐帧 + 逐装甲板） | ⚠️ **低于测量噪声**：关掉开关后实测 6105/6103/6042 μs，**反而略慢** |
| `infer_us` 的 `steady_clock` 计时 | 两次 `steady_clock` + 一次减法 ≈ **几十 ns/帧** |

⇒ ⭐ **结论：+5.7% 与自身波动同量级（±2%~4%），不能断定存在真实劣化。**

### 4.2 跟踪 —— 基本一致（三种测量一致）

### 4.3 规划 —— ⭐ **已查明：口径问题，实际一致**（见 §3）

已排除的原因：
1. ⭐ **MPC 求解器配置逐字相同**（`setup_yaw_solver` 两边完全一致，含 `max_iter = 10`）
2. ⭐ **`HORIZON / HALF_HORIZON / DT` 完全相同**（100 / 50 / 0.01）
3. ⭐ **本项目弹道槽位是纯透传**（`ideal.cpp` 只有 `return tools::Trajectory(v0, d, h);`）
4. ⭐ **日志/调试量不在计时范围内**（`LOG_PLANNER` / `LOG_SHOOTER` 是编译期宏，默认关）

**最可能的原因（但未能隔离验证）**：⚠️ **两边送入 `plan()` 的 `Target` 状态不同**。
实测同济的 tracker 在本段录像上**频繁发散**：
```
同济 benchmark 输出：'Target diverged!' × 19 次（667 帧）
本项目 CSV：trk_state = {lost:75, detecting:85, tracking:338, temp_lost:189}
```
发散状态下的 `Target` 其 `armor_xyza_list()` 与 `plan()` 的工作量均不同，
⇒ **该差异属于"运行状态不同"，不必然是本项目的架构开销。**

⚠️ **另一种可能**：本项目的 `pln_t_plan_us` 在**独立的规划线程**内测量，
   存在线程调度与锁竞争的干扰；同济 harness 为**同线程内联**测量。
   两种口径不完全等价。

📌 **待办**：把 `plan()` 的计时改为同线程内联一次，才能给出该阶段的确定结论。

## 5. 完整帧时间的构成（本项目，中位）

| 项目 | 耗时 | 占比 |
|---|---|---|
| **整帧** `t_frame_us` | **9961 μs** | 100% |
| ├ 录像解码/节流等待 `t_cam_wait_us` | 3756 μs | 38% |
| ├ **纯推理** `det_t_infer_us` | **5840 μs** | 59% |
| ├ PnP 解算 `sol_t_solve_us` | 367 μs | 4% |
| ├ 跟踪 `trk_t_track_us` | 419 μs | 4% |
| └ MPC 规划 `pln_t_plan_us` | 398 μs | 4% |

⭐ **纯算法 ≈ 7.0 ms/帧**（推理 + 跟踪 + 规划），**30 fps 预算 33 ms ⇒ 占用约 21%**。
⚠️ `t_cam_wait_us` 在录像模式下是**解码耗时**；真机上对应相机等待，不是算法开销。

## 6. 架构层面的明确差异（这些是确定的）

| 项 | 同济 | 本项目 |
|---|---|---|
| **检测窗口** | ⚠️ `YOLO(config, debug = true)` —— **默认开窗口**，`draw_detections` 内 `imshow` + `waitKey` | ⭐ **L3 通道，`wants_image()` 门控**，无人看图时**连 `clone()` 都不做** |
| **日志默认级别** | ⚠️ `console_sink` 与 `logger` 均设为 `debug`，且 `flush_on(info)` | ⭐ **运行期默认级别可调**，逐帧细节走**编译期宏**（默认关，零开销） |
| **逐帧细节日志** | ⚠️ `tools::logger()->debug("[Target] r=...")` —— **无条件求值**（参数先算再判断级别） | ⭐ `LOG_XXX(...)` 宏 —— **关掉时整条语句连同参数消失**（实测 1.65 ns vs 89 ns） |
| **调试输出（CSV）** | ❌ 无 | ⭐ `FrameDebug` → 54 列 CSV，可离线分析 |
| **热键 / 存图** | 部分硬编码 | ⭐ 运行期热键，零成本门控 |

⭐ **本次实测中，同济的日志量并不大**（44 行 / 2308 字节，因为该录像检测到的目标少）。
   ⚠️ **但在真机长时间运行、目标频繁发散的场景下，`flush_on(info)` 的刷盘开销会累积** ——
   **这一点本次未能量化**，不应夸大。

## 7. 结论

| 问题 | 结论 |
|---|---|
| 跟踪阶段是否变慢？ | 没有 —— 三种测量一致在 399~426 us（同济 406 us） |
| 规划阶段是否变慢？ | 没有 —— 同线程内联 272~281 us，与同济 284 us 一致；此前的 +43% 是异线程测量口径所致 |
| 检测阶段是否变慢？ | **尚无定论** —— 主循环口径 +4.4%，内联 harness 口径 +41%，两种方法可复现地分歧，根因未查明（已排除 frame_count / det-stats / ROI / CPU 频率） |
| 资源占用 | 纯算法约 6~8 ms/帧，30 fps 预算 33 ms，占用 18%~24%，余量充足 |
| 架构收益 | 可视化 / 日志 / 存图全部门控，默认零开销；同济默认开窗口 + debug 级日志 + 每帧 flush_on(info) |

### 本报告明确【未覆盖】的内容

- 内存占用（RSS / 堆分配次数）
- 多线程 CPU 总占用（本项目有独立规划线程）
- 真机相机路径（本报告全部基于录像回放）
- GPU / OpenVINO 设备差异（本机 GPU 不可用，全部 CPU 推理）
- 长时间运行的稳定性与热降频

这些需要真机环境，本轮无法测量。

## 8. 复现方式

```bash
# ① 编译同济原版（本机可直接配置）
cd vision_v2/upstream/sp_vision_25
cmake -S . -B /path/to/build -DCMAKE_BUILD_TYPE=Release && cmake --build /path/to/build --target auto_aim -j

# ② 编译对比 harness（本项目提供）
cd exp/bench && cmake -S . -B build && cmake --build build -j
cd vision_v2/upstream/sp_vision_25
./../../exp/bench/build/bench_tongji configs/demo.yaml <录像>

# ③ 本项目分段耗时
cd vision_v2/hzmir_vision
tools/scripts/run.sh infantry --enemy-color=blue --video=<录像> --video-speed=0 --force-mode=1 --csv=/tmp/ours
```
