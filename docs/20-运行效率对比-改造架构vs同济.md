# 运行效率对比：改造后架构 vs 同济原版

> **测量日期**：2026-10-04
> **硬件**：x86_64 工作站 · OpenVINO 2024.6.0（CPU 推理，无 GPU）
> **素材**：`assets/demo/demo.avi`（687 帧，1440×1080，30 fps）
> **方法**：**编译同济原版代码**，编写等价 harness，同一段录像、同一机器、同一时段测量

---

## 1. 为什么不是"读代码推断"，而是"真跑一遍"

最初的对比尝试（直接跑同济的 `tests/detector_video_test`）得到 **29.2 s**，
而本项目为 **7.5 s**，看似有 3.9 倍差距。**但该结论是错的**，原因：

```cpp
// 上游 tests/detector_video_test.cpp:73
auto key = cv::waitKey(33);      // 每帧固定睡 33 ms ⇒ 687 帧 ≈ 22.7 s
line 70: plotter.plot(data);     // 另接 PlotJuggler
```

⇒ **29.2 − 22.7 ≈ 6.5 s**，与本项目属同一量级。
**因此重新编写了 harness**（`tools/bench/bench_tongji.cpp`）：
- `YOLO(config, /*debug=*/false)` —— 关闭窗口
- 无 `waitKey`、不连 PlotJuggler
- 逐段计时：`detect` / `track` / `plan`

⭐ 上游 CMake **可直接在本机配置并编译**，因此这是**真机实测**而非推算。

## 2. ⚠️⚠️ 方法学教训：测量被【CPU 热降频】严重污染

**本节记录一个真实的测量陷阱**，因为不先解决它，任何数字都不可信。

同一份 `detect()`，在同一台机器上反复测量得到：

| 机器状态 | `det` 中位 |
|---|---|
| 刚冷却 | **5825 μs** |
| 连续跑数轮基准后 | **7780 ~ 8005 μs** |

⚠️ **差 35%**，且可复现。用不同迭代间隔进一步验证：

```
sleep=0us      median=7893us   ← 紧循环
sleep=2000us   median=7604us   ← 降 3.7%
sleep=10000us  median=6743us   ← 降 14.6%
sleep=0us      median=7876us   ← 再紧循环，回到 7876（可复现）
```

⇒ ⭐ **原因：YOLO 推理是 AVX 密集负载，连续满负载触发 CPU 降频**
（本机 i7-14700HX，标称最高 5.5 GHz，实测负载下 3.3~3.8 GHz）。

### ⭐ 因此采用的测量方法：**交替测量**

把两边**逐轮交替**执行（TJ → OURS → TJ → OURS …），使两边经历相同的热状态：

```
轮次    TJ det    OURS det   |  TJ track  OURS track  |  TJ plan  OURS plan
 1      5807us    5840us     |     283us     308us    |     233us     245us
 2      5889us    6000us     |     278us     306us    |     242us     252us
 3      5441us    5934us     |     281us     310us    |     227us     239us
 4      5837us    6094us     |     281us     313us    |     230us     239us
```

⚠️ **早期的非交替测量（曾得出 "+42%" 与 "−5%" 两种相反结论）已作废。**

## 3. ⭐⭐⭐ 最终结果（W141 重测 + 统计口径修正）

> ⚠️ **本节改过两次，如实记录**：
> · **W141 初版**报"跟踪 +13.2% / 规划 +8.7%" —— ⚠️ **那是【均值口径】，是伪差异**
> · **W142 修正**：查明 `track()` 是**双峰分布**，且两边**状态分布不同**
>   ⇒ ⭐ **改为按状态分层 + 用中位数**，真差异只有 **+3.7% / +3.8%**

### ⭐⭐ 关键方法学问题：`track()` 是双峰分布

```
track() 耗时分布（实测）
  · lost / detecting / temp_lost 帧 ≈  16 μs   ← 提前 return，不跑 EKF
  · tracking 帧                    ≈ 360 μs   ← 跑 update_target + EKF update
                            ⇒ 差 20 倍！
```
⚠️ **若直接用 `mean` 或"全帧中位"，结果会被【状态分布】污染** ——
   而两边的状态分布**本来就不同**（因为 detector 输出不同，见下）。

### ⭐ 为什么两边状态分布不同（不是架构差异，是**输入差异**）

| 每帧装甲板数 | 同济 | 本项目 |
|---|---|---|
| 0 个 | 193 | **167** |
| 1 个 | 424 | **435** |
| 2 个 | 67 | **80** |
| 3 个 | 3 | **5** |
| **平均** | **0.79 个/帧** | **0.89 个/帧** ⚠️ 多 13% |

| tracker 状态 | 同济 | 本项目 |
|---|---|---|
| `detecting` | 164 | 89 |
| `lost` | 135 | 77 |
| `temp_lost` | 128 | 159 |
| ⭐ **`tracking`** | **260~263** | **346~373** ⚠️ **多 43%** |

⭐ **因果链**：我们检测到的装甲板更多 ⇒ `set_target` 更容易成功 ⇒
   **`tracking` 帧更多** ⇒ 而 `tracking` 帧的 `track()` 贵 20 倍
   ⇒ ⚠️ **`mean` 被拉高** ⇒ 看起来"跟踪慢 13%"

### ⭐⭐⭐ 公平对比（同状态 + 中位数）

| 口径 | 同济 | 本项目 | 差异 |
|---|---|---|---|
| `det` **中位** | 6255 | 6240 | ⭐ **−0.2%**（基本一样） |
| ⭐ **`track`【只算 `tracking` 帧】中位** | **356** | **369** | ⭐ **+3.7%**（绝对 **+13 μs**） |
| ⭐ **`plan` 中位** | **240** | **249** | ⭐ **+3.8%**（绝对 **+9 μs**） |
| ⚠️ `track` 全帧 `mean` | 238 | 275 | ⚠️ +15.5%（**伪差异**，勿用） |
| ⚠️ `plan` `mean` | 196 | 225 | ⚠️ +14.8%（**伪差异**，勿用） |

⭐ **⇒ 真差异只有 3.7% / 3.8%，绝对量 9~13 μs。**
⚠️ **这也印证了：算法逻辑与同济基本一致 ⇒ 不该有大差异**（用户的判断是对的）。

### ⭐ 那 13 μs 从哪来（已排查）

逐项排查了所有代码差异，**唯一找到的确定性开销**：

| 项 | 同济 | 本项目 | 开销 |
|---|---|---|---|
| **EKF 额外求逆** | 无 | `S_prior.inverse()`（4×4）+ **`P_prior.inverse()`（11×11）** | ⭐ **实测 1.4 μs/次 update** |
| `data` map 插入 | 18 次 | 20 次 | 忽略 |
| `ArmorFilter` 临时构造 | — | 每次 track | ⭐ **实测 0.005 μs**（编译器优化掉了） |
| debug 结构 | — | `TrackerDebug`+`SolverDebug` | 各 32 B，忽略 |
| `Armor`/`Target` 成员 | — | — | **逐行比对，成员一致** |

⚠️ **1.4 μs 解释不了 13 μs**（需 9 次 update/帧，不可能）。
⭐ **⇒ 剩余部分落在测量不确定度内**：`track` 自身波动 **9.4%**（标准差 10.5 μs），
   13 μs 仅约 **1.2σ**。

### ⚠️ 方法与环境（如实记录）

· ⭐ **逐轮交替执行**（TJ → OURS → TJ → OURS …），消掉 CPU 热降频
  （W128 实测同一份 `detect()` 在冷/热态差 **35%**）
· ⚠️ 本机 `load average` **3.94**、CPU 频率 **800~5205 MHz** 剧烈波动 ⇒ 存在外部干扰
· ⭐ `track` 自身波动 **9.4%**（标准差 10.5 μs）· `plan` **21.1%**（标准差 15.4 μs）

## 3b. 整帧时间构成（本项目，中位）

**步兵**：
| 项 | 耗时 | 占比 |
|---|---|---|
| **整帧** `t_frame_us` | **9665 μs** | 100% |
| ├ 录像解码/节流 `t_cam_wait_us` | 3119 μs | 32.3% |
| ├ **推理** `det_t_infer_us` | **6250 μs** | 64.7% |
| ├ PnP 解算 `sol_t_solve_us` | 309 μs | 3.2% |
| ├ 跟踪 `trk_t_track_us` | 346 μs | 3.6% |
| └ MPC 规划 `pln_t_plan_us` | 341 μs | 3.5% |

⭐ **纯算法 = 推理 + 解算 + 跟踪 + 规划 = 7246 μs**
⚠️ `t_cam_wait_us` 在录像模式下是**解码耗时**；真机上对应相机等待，不是算法开销。

**哨兵**（W136 改用 MPC 后）：整帧 8326 μs = 推理 8042 + 解算 306 + 跟踪 343 + 规划 329

## 4. 逐阶段归因（已排除项）

### 4.1 `det` +2.5%

已逐项核对**完全相同**：
- ⭐ 输入：两者均为 **1440×1080 CV_8UC3**（探针实测），逐像素一致（前 20 帧差异为 0）
- ⭐ `compile_model` 配置：**逐字相同**（均 `device_` + `performance_mode(LATENCY)`）
- ⭐ 预处理：`resize` 到 640×640 + `ov::Tensor` 绑定，写法一致
- ⭐ 后处理：均每帧 `create_infer_request()`
- ⭐ `det-stats` 开关：A/B 实测**无系统差异**（7924/7780/8005 vs 7802/7828/7915）

⇒ 本项目多的仅为：一次 `steady_clock` 计时（几十 ns）+ 若干整数计数器（`n_pass`/`n_over_5/03/01`）。
⭐ **+2.5% 与轮间波动同量级，可视为无实质差异。**

### 4.2 `track` +10.1% —— 相对差异最大的一项

⭐ 本项目 `Tracker` 相对同济多做了：
- `ArmorFilter` 的**统一过滤**（颜色 / skip_names / 无敌 / 集火指令四道，同济部分规则在 `omniperception` 里）
- `priority_mode` 判断（默认不启用，仅一次布尔判断）
- `center_norm` 排序（W83 修复，取代同济的硬编码 1440×1080）
- `TrackerResult` 组装（含 `solver_dbg` 快照）

⚠️ **绝对量仅 +29 μs**，但**相对 +10%** —— 因为 track 本身基数小。

### 4.3 `plan` +4.5%

已核实**完全相同**：求解器配置（`setup_yaw_solver` 逐字一致，`max_iter = 10`）、
`HORIZON/HALF_HORIZON/DT`（100/50/0.01）、弹道槽位为**纯透传**
（`ideal.cpp` 仅 `return tools::Trajectory(v0, d, h);`）。

⚠️ **早期"plan +43%"的结论已作废** —— 那是**异线程测量口径**所致
（本项目 `pln_t_plan_us` 在独立规划线程内测得，含调度/锁竞争）。

## 6. 架构层面的明确差异（这些是确定的）

| 项 | 同济 | 本项目 |
|---|---|---|
| **检测窗口** | ⚠️ `YOLO(config, debug = true)` —— **默认开窗口**，`draw_detections` 内 `imshow` + `waitKey` | ⭐ **L3 通道，`wants_image()` 门控**，无人看图时**连 `clone()` 都不做** |
| **日志默认级别** | ⚠️ `console_sink` 与 `logger` 均设为 `debug`，且 `flush_on(info)` | ⭐ **运行期默认级别可调**，逐帧细节走**编译期宏**（默认关，零开销） |
| **逐帧细节日志** | ⚠️ `tools::logger()->debug("[Target] r=...")` —— **无条件求值**（参数先算再判断级别） | ⭐ `LOG_XXX(...)` 宏 —— **关掉时整条语句连同参数消失**（实测 1.65 ns vs 89 ns） |
| **调试输出（CSV）** | ❌ 无 | ⭐ `FrameDebug` → 54 列 CSV，可离线分析 |
| **热键 / 存图** | 部分硬编码 | ⭐ 运行期热键，零成本门控 |

⭐ **本次实测中，同济的日志量并不大**（44 行 / 2308 字节，因为该录像检测到的目标少）。
   ⚠️ **但在真机长时间运行、目标频繁发散的场景下，`flush_on(info)` 的刷盘开销会累积** ——
   **这一点本次未能量化**，不应夸大。

## 7. 结论

| 问题 | W142 修正后的结论 |
|---|---|
| **检测阶段是否变慢？** | ⭐ **没有** —— 中位 6240 vs 6255 μs，**−0.2%**（基本一样） |
| **跟踪阶段是否变慢？** | ⭐ **仅 +3.7%**（同 `tracking` 状态，中位 369 vs 356 μs = **+13 μs**） |
| **规划阶段是否变慢？** | ⭐ **仅 +3.8%**（中位 249 vs 240 μs = **+9 μs**） |
| ⚠️ **之前报的"跟踪 +13.2%"？** | ⚠️ **是伪差异** —— `track()` 双峰分布 + 两边状态分布不同（我们 `tracking` 帧多 43%），`mean` 被拉高 |
| **资源占用** | ⭐ 纯算法约 **7.2 ms/帧**（步兵）· **9.0 ms/帧**（哨兵） |
| **架构收益** | ⭐ 可视化/日志/存图**全部门控**；同济默认开窗口 + debug 级日志 + 每帧 `flush_on(info)` |

### ⭐ 与用户判断的印证

> 用户质疑：**"跟踪规划为啥慢了，不是基本是同济的算法逻辑吗？"**

⭐ **结论：用户判断正确。** 算法逻辑基本一致 ⇒ 真差异只有 **3~4%（9~13 μs）**：
· ⭐ **可解释的部分**：EKF 多 1 次 11×11 求逆（W9 加的 NIS/NEES 一致性诊断）≈ **1.4 μs**
· ⚠️ **其余落在测量不确定度内**（`track` 自身波动 9.4% = 10.5 μs 标准差，13 μs 仅 1.2σ）

### ⚠️ 本报告明确【未覆盖】

- 内存占用（RSS / 堆分配次数）
- 多线程 CPU 总占用（本项目有独立 plan 线程）
- 真机相机路径（全部基于**录像回放**）
- GPU / OpenVINO 设备差异（本机 GPU 不可用，全部 CPU 推理）
- 长时间运行稳定性（本报告反而**证明了**长时间运行会降频）
- 四兵种中只测了 `infantry`
